## 为什么做 LumbarOS？

绝大多数腰靠都是静态的。

它默认人的身体会一直待在产品预设的位置。

但人不会。

我们会向前探身、向后靠、改变坐深、移动重心；工作时间越长，想要的支撑强度也会发生变化。

**LumbarOS 想把“腰靠”从一个静态部件，变成一个真正的闭环人机系统。**

\`\`\`text
感知 TOUCH  →  理解 UNDERSTAND  →  调节 MOVE  →  再次感知 FEEL AGAIN
     ▲                                              │
     └──────────────────────────────────────────────┘
\`\`\`

V1 在 WTCC 2026 黑客松周期内完成，目标不是一次性解决“人体舒适度”这个复杂问题，而是先证明最关键的闭环可以真实运行：

> **感知身体接触 → 记住用户认可的支撑状态 → 控制活动腰托前顶 / 保持 / 回退 → 再读取新的接触状态。**

V2 将在此基础上进一步升级为一个**数据与模型驱动的个体化支撑系统**。

## 硬件

- **Arduino Nano** 作为嵌入式控制核心
- **16×16 ViTac 柔性压力感知阵列**
- JSON 串口数据输出
- 从触觉矩阵映射到 **8 个实际身体接触区域**
- 主动剪式伸缩腰托机构
- 可编程执行 **前顶 / 回退 / 停止**
- 电脑端串口与控制接口，为快速联调预留完整边界

V1 采用剪式伸缩机构，通过电机驱动腰托面板向人体方向运动。

这意味着腰托不是“被动靠垫”，而是一个会主动改变人与设备接触关系的执行机构。

原始硬件交接、BOM 与机构资料均保留在本仓库中。

## 软件

- 触觉帧实时解析
- 16×16 → 8 区域聚合
- 零点 / 基线校准
- 无硬件模拟器
- 用户个人舒适支撑状态记录
- 有边界的 **前顶 / 保持 / 回退** 自动控制
- 接触丢失保护
- 数据超时保护
- 饱和 / 异常状态保护
- 会话记录与回放
- 电脑端 Web 控制界面
- 控制器、设备解析、服务层与安全边界测试

# V1 的核心控制逻辑

V1 的思路非常直接：

1. 用户先手动找到自己觉得舒服的支撑状态。
2. 点击“记住当前支撑”。
3. LumbarOS 记录一小段稳定的触觉状态，形成个人参考。
4. 正常呼吸和轻微移动落在允许区间内，不触发动作。
5. 接触持续偏弱时，腰托可以在受限范围内向前跟进。
6. 接触持续偏强或局部明显过载时，腰托可以回退让位。
7. 每次运动后，等待接触重新稳定，再进入下一轮判断。

**V1 的价值，是建立一个之后可以被数据和模型超越的真实基线。**

---

# 真正困难的问题：压力不是静态的

LumbarOS 的腰托会主动向前运动。

所以压力变化是一个**动态耦合过程**：

- 人移动，会改变压力；
- 腰托移动，也会改变压力；
- 腰托继续前顶，甚至会推动人的身体改变位置。

因此：

> **压力升高 ≠ 一定是“人向后靠”**  
> **压力降低 ≠ 一定是“人向前移动”**

这也是我们认为这个项目真正有技术价值的地方。

LumbarOS 需要把**触觉状态、用户状态和执行器状态**放在同一个闭环里理解。

V1 先用有边界的反馈控制解决问题。

V2 则会进一步用真实交互数据和学习模型处理这种动态关系。

# V2 · Learn · Adapt · Breathe

> **预计在 V1 之后约两个月进入下一阶段。**

V2 的目标不是简单“换一个更复杂的算法”。

而是让 LumbarOS 从一个**可以工作的控制器**，升级成一个**真正理解个体偏好的主动支撑系统**。

---

## 01 · 真人数据

我们计划采集多轮真实用户交互数据。

核心数据结构：

\`\`\`text
身体属性
   ×
姿态 / 当前任务
   ×
触觉状态
   ×
腰托动作
   ×
用户舒适反馈
\`\`\`

例如：

- 身高 / 体重
- 当前坐姿与任务状态
- 8 区压力及其时间变化
- 腰托前顶 / 回退的动作
- 用户认为“偏弱 / 合适 / 偏强”
- 用户主动重新调节的记录

我们关心的不是简单堆积几十万帧。

真正重要的数据单元是：

> **一次完整的“状态 → 调节 → 接触变化 → 用户评价”的支撑交互。**

---

## 02 · 个人偏好学习

V2 不再假设存在一个对所有人都适用的“正确支撑力”。

系统将逐渐学习：

- 用户喜欢多强的支撑
- 可接受的压力波动范围
- 用户移动多久后才应该跟随
- 前顶速度与力度偏好
- 后靠时的让位速度
- 工作、休息等不同场景下的支撑差异

**同一把腰托，面对不同的人，最终应该形成不同的行为。**

---

## 03 · 大模型层

计划中的首轮基线：

### **Qwen2.5-7B-Instruct + LoRA 领域微调**

但大模型**不会直接实时控制电机**。

实时运动仍然交给确定性的底层控制器。

大模型主要负责：

### 理解用户需求

例如：

> “现在这个力度挺舒服，但我往前拿东西的时候不要马上追过来。”

这不是一个简单的“加 10% / 减 10%”。

它同时包含：

- 当前支撑强度认可
- 跟随速度偏快
- 希望对短时前倾增加等待时间

### 形成支撑策略

大模型把自然语言需求、当前触觉状态与历史个人偏好组合成**经过范围检查的策略参数**。

底层控制器再负责实际执行。

---

## 04 · 持续个体适配

产品进入真实家庭使用后，我们希望它逐渐变成：

**越坐，越懂你。**

但 V2 不会让设备每天在家里随意修改 7B 模型权重。

实际路线是：

### 本地快速适配

优先更新：

- 用户支撑参考
- 用户偏好参数
- 个人轻量模型
- 不同场景的支撑策略

### 全局模型升级

积累足够真实数据后：

- 数据清洗
- 形成领域指令数据
- LoRA 离线训练
- 独立评测
- 再发布新的公共模型版本

这样可以同时获得：

**个体快速适应 + 公共模型持续进化**

---

## 05 · 呼吸灯：让机器状态变得可感知

V2 计划加入克制的呼吸灯交互。

不是为了装饰。

它是设备状态语言。

例如：

- **轻柔呼吸**：系统在线 / 正在感知
- **学习动画**：正在记录个人舒适参考
- **流动变化**：腰托正在调节
- **稳定常亮 / 微呼吸**：当前支撑稳定
- **保护提示**：暂停、接触异常或安全状态

我们的目标是：

> 用户不需要一直盯着电脑或 App，也能知道设备此刻在做什么。

# 运行 V1 Demo

无需连接硬件即可运行模拟模式：

\`\`\`bash
python run.py
\`\`\`

使用真实串口传感器前：

\`\`\`bash
python -m pip install -r requirements-serial.txt
\`\`\`

随后按照以下文档完成区域映射和硬件适配：

- [docs/HARDWARE_INTEGRATION.md](docs/HARDWARE_INTEGRATION.md)
- [docs/implementation-contract.md](docs/implementation-contract.md)

> 在真实执行器的方向、行程限制、单位、超时与应答机制完成实物验证以前，不应直接启用真实自动运动输出。
